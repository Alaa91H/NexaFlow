## Provisional research boundary

The next release should favor a narrow reliability improvement with durable local evidence, deterministic tests, no telemetry or new permissions, and no generic automatic replay of uncertain side effects. Candidate areas to inspect in source are lifecycle cleanup on automation disable/delete, one-shot time-alarm late-delivery policy, and source-specific migration of remaining legacy direct-exit monitors.

## Android 17 cellular-capability evidence — 2026-08-27

The live issue is now diagnosed at the model boundary. `getAllowedNetworkTypesForReason(USER)` reads the configured user restriction, not the modem's capability ceiling. Using it as `selectableMask` means a user who currently has GSM-only configured sees only GSM in the dynamic profile picker; the picker itself merely renders the upstream `options` list.

AOSP exposes `TelephonyManager.getSupportedRadioAccessFamily()` as the modem-supported radio-access-family bitmask. It requires `READ_PRIVILEGED_PHONE_STATE` or carrier privilege. The public implementation delegates to `ITelephony.getRadioAccessFamily(phoneId, callingPackage)`, and the service implementation receives a phone/slot id, performs the privileged-phone-state or carrier check, then obtains the radio access family from `ProxyController`. Therefore a correctly elevated UserService can attempt this exact read with a physical slot; ordinary app process access may remain unavailable even with `READ_PHONE_STATE`.

AOSP separately maps the system default network-mode property to known RAT masks through `RadioAccessFamily.getRafFromNetworkType`. Its closed `RILConstants` table defines modes 0–33; e.g. 9 is LTE+GSM+WCDMA, 22 is LTE+TD-SCDMA+CDMA+EVDO+GSM+WCDMA, 23 is NR-only, and 24–33 are defined NR combinations. This supports a bounded root fallback only when `ro.telephony.default_network` yields a known integer. It is a device default profile rather than a carrier-authoritative per-subscription capability, so UI and diagnostics must name that limitation and every write must retain per-subscription read-back verification.

There is no discovered AOSP `cmd phone` command that returns supported radio access family. The documented `get-allowed-network-types-for-users` command returns only the USER reason. No `dumpsys` parser will be added because its textual format is diagnostic and was not verified as a stable capability contract.

## v3.50.2 implementation decision — 2026-08-27

### Scheduled automatic execution

Android documentation confirms that a revoked `SCHEDULE_EXACT_ALARM` cancels future exact alarms, and that the app must re-check `canScheduleExactAlarms()` and reschedule its current state after the permission is granted. NexaFlow already owns immutable occurrence records and uses `RTC_WAKEUP` with `setExactAndAllowWhileIdle` when access exists. The remaining operational gap is that its Root bulk-grant path verifies access but does not explicitly cause the scheduler to rebuild its occurrences; relying only on a platform grant broadcast is insufficient for a root `appops` repair path.

The implementation will therefore send a package-scoped, explicit scheduler-recheck broadcast only after the existing final verification confirms exact-alarm access in an application context. `AutomationAlarmReceiver` will accept that private recheck action and run the same durable reconciliation/reschedule path as the platform permission-change event. The manifest will also list the END action handled by the receiver, eliminating ambiguity for hardened intent matching. It will not fabricate a timer or silently convert an exact task into a claimed punctual task: `RTC_WAKEUP` + `setExactAndAllowWhileIdle` remains the path when access is available, while Android's documented inexact fallback remains visibly constrained by the platform if special access is absent.

### Cellular profile picker

The picker will select profiles in this order: (1) the public modem-supported mask intersected with the readable carrier mask, if available; (2) the exact elevated `ITelephony.getRadioAccessFamily(slot)` modem mask when a Shizuku UserService can perform the privileged binder read; (3) a strict parser for a known `ro.telephony.default_network` integer read via a closed root/Shizuku operation; and only then (4) the elevated USER mask as a last-resort current configuration, which is labelled as such. No fallback synthesizes a universal 2G/3G/4G/5G menu. The default-profile fallback is a device capability hint, not carrier confirmation, so its label and diagnostics will say that the carrier may reject a profile and `NetworkModeController` will continue to require subscription-scoped read-back before reporting success.

### Test commitments

The change will add pure tests for all supported default-network property forms (single-SIM, slot-indexed multi-SIM, invalid/out-of-range), for exact profile mapping such as RIL modes 9, 22, 23, 24, and for rejecting unknown values. It will add contract tests for the new closed elevated operation. Scheduler tests will pin the private recheck action and manifest/receiver action coverage where feasible. No local Gradle task will be run; acceptance stays in the remote repository CI.
