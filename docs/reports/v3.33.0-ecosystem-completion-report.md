## 2. الملفات المعدلة

تضمنت التعديلات `CapabilityModels.kt` و`Constraint.kt` و`Automation.kt` و`Workflow.kt` و`WorkflowInterpreter.kt` و`ExecutionEngine.kt` و`AppModule.kt` و`AppTriggerAccessibilityService.kt` و`CommandCatalog.kt` وطبقة Shizuku/AIDL/Root. كما عُدلت شاشات بناء/عرض الأتمتة، و`PermissionManagerScreen`، وترجمات الإفصاح في اللغات المدعومة. تم ذلك بصورة additive للحفاظ على العقود وبيانات الأتمتة القديمة.

## 3. بروتوكولات Plugin المدعومة

يدعم الإصدار حد Locale/Tasker العام الموثق لإجراءات Plugin وشرط Plugin، ومسار Event مقيد حيث يمكن إثبات هوية مرسل broadcast. لا يعتمد على reflection أو على كود منافس مملوك، ويظل إدخال Android objects إلى `RuntimeValue` محظوراً. تستند حدود البروتوكول إلى مواصفة Locale العامة [1] وقيود مستقبلات Android الموثقة [2].

| البروتوكول | الحالة | الدليل والحد |
|---|---|---|
| Locale-compatible action | **مدعوم** | ordered broadcast صريح عبر `PluginFireClient` و`PluginCapabilityBackend` |
| Locale-compatible condition | **مدعوم** | `ACTION_QUERY_CONDITION` و`PluginConditionBackend` بنتيجة typed |
| Plugin event | **جزئي/مقيد** | Android 14+ فقط، package/component approval وsender identity؛ لا direct workflow execution |
| Tasker/Locale غير الموثق | **غير مدعوم** | لا تُخمن extras أو callbacks غير موثقة |

## 4. Plugin Actions المدعومة

تُنفذ Action من instance محفوظ وموافق عليه فقط. تُستخدم مهلة، نتيجة ordered broadcast، وdiagnostic منظم. لا يعني acknowledgement أن الأثر الخارجي تحقق؛ لذلك تظل verification مستقلة أو غير متاحة حسب البروتوكول.

## 5. Plugin Events المدعومة

يعالج `PluginEventReceiver` الطلبات ضمن حدود payload ثم يمررها إلى `PluginEventIngress` حيث تطبق مصادقة المصدر وdeduplication بـ event/correlation identifier وrate limit. النتيجة الوحيدة هي `NexaFlowEvent` المنشور إلى `EventBus`، ثم المطابقة عبر `TriggerIndex`، ثم `PluginEventRouter`. لا يتصل receiver بـ `ExecutionEngine` مباشرة. على Android 14+ تتوفر واجهات تحقق sender لمستقبلات dynamic المقيدة؛ الإصدارات الأدنى لا تعلن هذا المسار كدعم آمن [2].

## 6. Plugin Conditions المدعومة

تُعاد حالات `Satisfied` و`Unsatisfied` و`Unknown` و`Unavailable` و`Error(reason)` عبر `ConditionResult`. لا يحول `AutomationConstraintGate` حالة `Unknown` إلى `false`. ولا يمكن إنشاء شرط Plugin من واجهة المستخدم كبيانات ناقصة؛ يعرض فقط عند استيراد/حفظ instance موثق.

## 7. عدد القدرات الأصلية

يتضمن `CapabilityId` الحالي **22 معرّفاً**. في هذه الدفعة، أضيفت/رُبطت **9 عمليات أصلية مميزة أو مقيدة**: `PACKAGE_FORCE_STOP`، `SYSTEM_SETTING_WRITE`، `FILE_COPY`، وست عمليات Accessibility (`find`، `click`، `scroll`، `input text`، `wait for node`، `gesture`). كما توجد قدرة خارجية واحدة `PLUGIN_CONDITION_READ` إلى جانب `PLUGIN_ACTION`.

## 8. عدد المشغلات

يحتوي `TriggerType` على كتالوج قائم واسع، وأضيف `PLUGIN_EVENT` إليه. يظل دعم هذا المشغل **مشروطاً** بـ Android 14+ ووجود Plugin instance معتمد ومفهرس؛ لذلك لا يساوي مجرد وجود enum ضمان تشغيله على كل جهاز.

## 9. عدد الشروط

القيود legacy تبقى بسيطة ومتوافقة. أضيف نوع `ConstraintType.PLUGIN` وبوابة typed للشرط الخارجي. الشروط المنطقية المركبة، precedence شاملة، وكتالوج sensor/location واسع ليست مكتملة للمستخدم النهائي في هذا الإصدار.

## 10. قدرات التحكم بالتدفق

توسع interpreter الوحيد بعقد `DelayNode` و`RetryNode` و`TimeoutNode` و`RaceNode` و`WhileNode` و`TryNode` و`WaitUntilNode`، إلى جانب Sequence/Parallel/Branch/Loop الموجودة. الدلالات bounded وتعاونية مع coroutine cancellation، وتغطيها اختبارات مباشرة. هذه العقد **داخلية ومبرمجة فقط حالياً**؛ لم تضف بعد إلى serialization الخاص بـ `Automation` أو محرر شجرة workflow. التفاصيل في [وثيقة الحالة](../architecture/workflow-flow-control-status.md).

## 11. قدرات تحويل البيانات

يبقى `RuntimeValue` التمثيل canonical. يوفر `ExpressionEngine` المقارنات المنطقية والعددية والنصية و`length`/`lower`/`upper`/`contains`/`exists` من دون `eval` أو reflection. JSON query/map/reduce/template engine واسعة ليست مدعومة أو معلنة في هذا الإصدار.

## 12. الخلفيات

| الخلفية | الحالة | الضمان |
|---|---|---|
| Android public API / Intent | مدعومة حسب descriptor | allowlist وvalidation قائمين |
| Plugin | مدعومة للـ action/condition | instance محفوظ وموافقة وبروتوكول محدود |
| Shizuku | مدعومة للعمليات typed | UserService AIDL فقط؛ لا reflection ولا fallback صامت |
| Root | مدعومة للعمليات typed | allowlisted `PrivilegedOperation` و`SafeCommandBuilder` |
| Accessibility | مدعومة مقيدة | consent + service + active package + selector محدود |
| ADB | غير متاحة في التطبيق العادي | `ADB_UNAVAILABLE` منظم، غير مسجلة كقناة إنتاج وهمية |

## 13. استراتيجيات التحقق

تظل verification مركزية في `CapabilityExecutionService`. Plugin action لا يختلق proof خارجي، وAccessibility لا تعلن نجاحاً إذا رفضت النافذة العملية. التحقق الكامل لحالة UI المرئية، read-back لكل setting، وتحقيق HTTP/file شامل ما زال جزئياً ويجب ألا يتحول `UNKNOWN` إلى success.

## 14. ضوابط الأمان

تتضمن الضوابط: allowlists للـ package/settings/file، منع generic workflow shell، عدم تمرير `Bundle`/`Parcelable`/`Intent`/`Binder` إلى `RuntimeValue`، قيود depth/size للـ payload، package/component approval، rate limiting، deduplication، حدود وقت، selector محدود، وحصر Accessibility في الحزمة صاحبة النافذة النشطة. وثائق Android Accessibility تؤكد أن الخدمة تحتاج إفصاحاً واستخداماً ضمن غرض واضح [3].

## 15. متطلبات الصلاحيات

تعتمد كل قدرة على descriptor وسياستها. تتطلب Accessibility: إقرار إفصاح داخل التطبيق ثم تمكين Android AccessibilityService. تتطلب Shizuku grant فعلي وUserService متصلاً. تتطلب Root موافقة superuser. وتتطلب Plugin identity/configuration approved. لا تقوم الخلفيات بالتدرج تلقائياً بين Root وShizuku.

## 16. توافق Android

Plugin event الآمن مقيد بـ Android 14 / API 34 فأعلى بسبب شرط sender identity. الباقي يخضع إلى `minAndroidApi` في descriptors والـ public APIs المتاحة. لا يعلن ADB authority داخل تطبيق Android عادي.

## 17. قدرات Root

Root ينفذ عمليات typed محصورة في package operations وإعدادات allowlisted وfile copy مسيطر عليه. لا يعرّض `executeArbitraryShell(command)` كقدرة workflow.

## 18. قدرات Shizuku

Shizuku ينفذ مجموعة العمليات typed نفسها عبر UserService AIDL وargv يعاد بناؤه داخلياً. أعيدت حالات binder/service/grant إلى `SHIZUKU_UNAVAILABLE` أو `SHIZUKU_DENIED` منظمة. أزيل `Shizuku.newProcess` reflection من المسار الجديد؛ توثق واجهات Shizuku العامة نمط UserService [4].

## 19. قدرات Accessibility

تنفذ الخلفية: find node، click، scroll، input text، wait for node، وgesture tap-like مقيد. traversal محدود إلى 2,000 node، selector محدود إلى view-id/text/content-description، والعملية ترفض الحزمة غير المطابقة أو service غير المتصلة أو العقدة stale. long click، wait for text، inspect tree الخام، والتحقق المرئي المتقدم غير معلنة كدعم.

## 20. قدرات ADB

الحالة: **غير متاحة** في التطبيق العادي. تعيد `AdbCapabilityBackend` الحالة المنظمة `ADB_UNAVAILABLE` ولا تدخل `CapabilityRegistry` الإنتاجي. هذا تنفيذ صادق لحد البيئة وليس capability وهمية.

## 21. عدد الاختبارات

نفذت بوابة الوحدات الشاملة **831 اختباراً** بالنتيجة صفر failures وzero errors وzero skipped. يوجد 131 ملف اختبار Kotlin في المشروع عند الحصر، مع اختبارات جديدة لمسارات Plugin conditions/events وprivileged backends وAccessibility وworkflow flow-control.

## 22. عدد اختبارات التكامل

اختبارات Robolectric/Android unit الموجودة تغطي ordered broadcast والـ receivers وpayload boundaries وخدمة Android، لكنها ليست اختبارات جهاز فعلي مستقلة. لذلك لا يعلن هذا التقرير عدداً لتكامل device-level؛ الحالة **0 اختبارات جهاز فعلية موثقة في هذه الدفعة**.

## 23. نتائج الضغط

لا أُجريت stress suite بعدد آلاف workflows أو catalogue fan-out في هذه الدفعة، لذا الحالة **غير مقاسة**. توجد حدود تشغيلية فعلية: حد 1,000 loop iteration، payload bounded، dedup/rate-limit للأحداث، وtraversal Accessibility محدود.

## 24. نتائج الفشل والاستعادة

اختبرت الحالات المنظمة لـ plugin condition غير الموثوق/غير المتاح و`UNKNOWN`، payload Parcelable المرفوض، Shizuku/Root/ADB غير المتاحة، Accessibility غير المتصلة، timeout/retry/race، وإلغاء coroutine. لا يوجد ادعاء بأن كل سيناريو process death على جهاز فعلي قد اختبر.

## 25. قياسات الأداء

لا توجد benchmark رقمية صالحة في هذه الدفعة؛ الحالة **غير مقاسة**. يمنع التصميم scan كامل للـ workflows في مسار Plugin event عبر `TriggerIndex`، ويضع payload/rate/node/loop bounds. يلزم benchmark مخصص قبل ادعاء latency أو throughput.

## 26. القدرات غير المدعومة

تشمل: ADB العادي، generic shell workflow، وصول Plugin إلى repositories/vault/runtime objects، Plugin events غير القابلة للتحقق على API <34، long click/inspect raw UI tree، UI automation غير المقيدة، التحويلات المتقدمة غير المذكورة، وكتالوج native/trigger/condition الشامل المبين في المواصفة.

## 27. القيود المعروفة

يبقى `AppTriggerAccessibilityService` القديم يستخدم تشغيل foreground مباشر في مسار trigger legacy؛ لا يقلد backend الجديد هذا النمط، لكن توحيده الكامل مع EventBus/TriggerIndex مؤجل. كما أن عقد flow-control الجديدة ليست persistence/UI للمستخدم النهائي بعد. وتبقى UserService method legacy محصورة لتوافق `SystemController` وليست capability جديدة.

## 28. الدين التقني

الأولوية التالية هي نقل trigger sources القديمة إلى EventBus/TriggerIndex، ترقية serialization عبر workflow versioning، استكمال validation/dry-run للـ conditions/triggers الجديدة، وإضافة اختبارات جهاز فعلي وstress/performance benchmarks. يلزم أيضاً ترحيل compatibility-only generic shell callers إلى العمليات typed قبل إزالة method legacy نهائياً.

## 29. الانحرافات المعمارية

لا يوجد runtime أو resolver أو TaskManager أو EventBus أو TriggerIndex أو recovery path موازٍ أُنشئ في الدفعة. الانحراف الوحيد الموثق هو استمرار legacy trigger/direct execution في مصادر موجودة سلفاً، وهو مسجل كدين وليس مساراً جديداً. كل المسارات الجديدة تمر إما بـ `CapabilityExecutionService`/`CapabilityRegistry` أو EventBus→TriggerIndex وفق نوعها.
