# تصميم NexaFlow الأدنى لواجهة ديناميكية واعية بالقدرات

**الأساس:** v3.37.1، بعد تدقيق المستودع والأدلة الرسمية.  
**القرار المعماري:** توسيع مصدرين موجودين فقط: `CommandCatalog` لتوافق Action/Trigger و`CapabilityRegistry` للحالة الحية للـbackend. لا يضاف scheduler أو permission manager أو action registry موازٍ.

## مبدأ المصدر الواحد للحقيقة

يُنتج `CapabilityStateStore` singleton لقطة `StateFlow` محدودة من availability الحية. يجمع المتجر `CapabilityDiagnostics` للـdescriptors المسجلة مع مدخلات التوافق الحالية من `CommandCompatibilityEngine`. لا يمنح المتجر أي إذن ولا ينفذ action؛ هو يصف ويحلل فقط.

```text
Device / permission / backend callback
        ↓ invalidate
CapabilityStateStore.refresh()
        ↓ bounded snapshot
CapabilityRegistry + CapabilityResolver + CommandCompatibilityEngine
        ↓
Action / Trigger / Template / Workflow requirement resolution
        ↓
Builder picker, search, template list, workflow admission, Capability Center
```

## العقود الجديدة أو الموسعة

| العقد | المسؤولية | حد السلامة |
|---|---|---|
| `CapabilityRequirement` في Domain | تعبير نقي: `AllOf` و`AnyOf` و`Not` و`Capability` و`None` | لا يقرأ Android ولا يكشف Root أو Shizuku مباشرة. |
| `CapabilityRequirementResolver` في Domain | يحول snapshot إلى `Available` أو `Unavailable` مع requirement مفقود | يختبر AND/OR/NOT حتمياً. |
| `CapabilityStateStore` في Core | cache `StateFlow` وinvalidate/refresh للـreports المسموح بها | لا polling دائماً؛ لا يستعلم كل frame. |
| `CommandRequirementCatalog` | يربط Action/Trigger/Template بالـrequirement الحقيقي أو `None` | يعيد استخدام `CommandCatalog` كحقيقة توافق Android الحالية ولا ينسخ جدوله. |
| `CapabilityAwareCatalog` | يدمج CommandCompatibility + capability resolution للقوائم المتاحة فقط | لا يترك options غير المتاحة disabled في picker أو search. |
| `WorkflowCapabilityValidator` | يمنع enable/run عندما requirement الفعلي غير محلول | لا يحذف workflow المستورد؛ يعيد diagnostic typed. |

## حالات القدرة

تبقى `CapabilityAvailability` الحالية لإشارة backend منخفضة المستوى، ويضاف عرض تشخيص typed أعلى مستوى يميز: **متاح، غير متاح، صلاحية مطلوبة، Shizuku مطلوب، Root مطلوب، Device Owner مطلوب، Android غير مدعوم، تحقق فشل، غير مدعوم**. يتحول السبب من تقارير backend و`CommandSpec` ولا يُولد من نصوص UI.

## قواعد الفلترة

1. يبقى `CompatibilityGate` نقطة الفلترة الوحيدة لمحرر الأتمتة، لكنها تتحول من snapshot `remember(context)` إلى مخرج state-aware يدمج `CommandCompatibilityEngine` مع resolver.
2. القوائم التي تغذي actions وtriggers والبحث ومحتوى الفئات تُشتق من المخرج نفسه؛ لذلك لا يمكن أن يظهر action في search وهو مخفي في picker.
3. `RoutineTemplateCatalog` يفحص requirement المجموع لكل actions/triggers قبل أن يظهر template أو يطبقه.
4. عناصر workflow المحفوظة أو المستوردة لا تختفي من البيانات؛ يمنع validator تفعيلها أو تشغيلها ويعيد identifiers مفقودة واضحة لمركز القدرات والسجل.
5. مركز القدرات فقط يعرض العناصر غير المتاحة، مع السبب، ولا ينفذ grant أو root/shizuku command.

## حدود Root وShizuku وManaged Device

| المجال | ما سيدخل في الدفعة | ما يبقى مخفياً أو غير مدعوم |
|---|---|---|
| Shizuku | الحالات الحية الموثقة الحالية: server، permission، UserService، والعمليات typed الأربع | package manager عام، silent install، filesystem عام، أو أي فعل لم يملك backend typed. |
| Root | availability الحية لعمليات force stop، package enabled state، setting allowlist، controlled copy | root filesystem وsilent install وكل privilege افتراضي. |
| Device Owner | detector تشخيصي لوضع التطبيق الحالي فقط | لا enterprise action/Managed Play حتى backend موثق ومختبر. |
| ADB | سبب تشخيص صريح غير متاح | لا قناة ADB ضمن تطبيق Android عادي. |

## تحديثات الحالة والأداء

تحدث اللقطة عند بدء التطبيق/استئنافه، ونتيجة تدفق request permission، وتغير accessibility، وcallbacks Binder الخاصة بـShizuku عند توفر التكامل القائم. لا تستخدم مهمة دورية أو polling. Root يعاد التحقق منه عند refresh صريح أو قبل privileged run فقط، لا أثناء recomposition.

## الترتيب التنفيذي

1. Domain requirement expression + resolver + tests.
2. State store فوق registry والـcompatibility مع backends/managed detector قابلة للحقن.
3. فلترة builder/search/templates من المخرج الموحد.
4. تعميم Capability Center إلى diagnostics reactive مع الترجمات.
5. workflow admission ثم اختبارات الوحدة/التكامل/الواجهة.

## معايير رفض صريحة

يرفض التصميم أي mapping يدعي أن وجود Shizuku أو Root يجعل capability متاحة، وأي `if (root)` أو `if (shizuku)` في Compose، وأي إضافة لصلاحيات تثبيت أو وصول تخزين واسع. كما يرفض وصف Google Play update أو Managed Play كقدرة قابلة للتنفيذ قبل backend رسمي قابل للتحقق.
