# NexaFlow v3.37.1 — تدقيق نظام واجهة ديناميكية واعية بالقدرات

**تاريخ التدقيق:** 20 أغسطس 2026  
**النطاق:** مستودع NexaFlow عند `v3.37.1` قبل أي توسعة جديدة لنظام القدرات.  
**المنهج:** تتبع نقاط الإدخال والتنفيذ وحقن الاعتمادات والمستهلكين الفعليين؛ لا تُصنف فئة أو interface وحدها كقدرة إنتاجية.

## النتيجة التنفيذية

يوجد في NexaFlow بالفعل **نواة تنفيذ قدرات حقيقية**: `CapabilityRegistry` و`CapabilityResolver` و`CapabilityExecutionService`، مع backends عامة وامتيازية تفحص حالتها عند كل request. كما أن محرر الأتمتة يملك `CompatibilityGate` واحداً يفلتر قوائم الاختيار والبحث من خلال `CommandCompatibilityEngine`.

لكن لا يوجد بعد **مصدر حالة تفاعلي موحد** يصل بين availability الخاصة بالـbackends وواجهة البناء والقوالب ومركز القدرات. لهذا فإن تنفيذ الطلب الصحيح هو توسيع هذه المكونات القائمة، لا إنشاء محرك صلاحيات أو scheduler أو registry ثانٍ.

| المكوّن | الحالة المثبتة | الدليل | الفجوة المحددة |
|---|---|---|---|
| Capability model | **REAL_CODE / UNIT-TESTABLE** | `domain/capability/CapabilityModels.kt` | حالات availability أقل تفصيلاً من المطلوبة، ولا توجد requirement expressions مركبة للإجراءات/المحفزات. |
| Capability registry | **REAL_CODE** | `CapabilityRegistry` محقون singleton في `AppModule` | يضم descriptors/backends لكنه لا ينشر `Flow` لحالة الجهاز أو snapshot cache. |
| Capability resolver | **REAL_CODE** | يقيّم policy ويستعلم backend health ويختار channel آمن | يحل request فردياً فقط؛ لا يقدّم catalog filtering أو AND/OR/NOT metadata. |
| Capability verification | **REAL_CODE / PARTIAL** | `CapabilityExecutionService.verifyIfNeeded` | verification post-condition متاح للـbackend المنفذ فقط؛ لا توجد مصفوفة تشخيص تشغيلية طويلة العمر. |
| Android public backend | **REAL_CODE** | `AndroidPublicCapabilityBackend` وcatalog | لا يُستهلك من UI لإخفاء Action/Trigger. |
| Shizuku availability | **REAL_CODE / PARTIAL** | `ShizukuCapabilityBackend`: server + grant + UserService + selection policy | يغطي أربعة operations typed فقط؛ لا يعني package install أو كل system operation. |
| Root availability | **REAL_CODE / PARTIAL** | `RootCapabilityBackend`: root availability + typed operation mapping | يغطي أربعة operations typed فقط؛ لا يثبت root filesystem أو silent install أو package manager العام. |
| ADB | **UNSUPPORTED** | `AdbCapabilityBackend` يعيد unavailable صراحة وغير مسجل إنتاجياً | لا توجد قناة ADB موثقة لتطبيق Android عادي. |
| Managed/Device Owner | **CONTRACT GAP** | لا يوجد backend أو descriptor فعلي في registry | لا يجوز عرض Managed Google Play أو enterprise package operations. |
| Action capability mapping | **PARTIAL** | `CapabilityActionMapper` يربط OPEN_URL وOPEN_SETTINGS وplugin فقط | معظم `ActionType` تظل على handlers legacy ولا تعلن requirement موحداً للواجهة. |
| Trigger capability mapping | **UNSUPPORTED** | لا يوجد mapper/registry requirements للمحفزات | UI لا يستطيع إخفاء trigger بالـruntime capability. |
| Builder filtering | **PARTIAL** | `CompatibilityGate` + `AutomationOptionCatalog` + `AutomationBuilderScreen` | يعتمد DeviceProfile snapshot داخل `remember(context)` وليس availability runtime أو Flow. |
| Search filtering | **PARTIAL** | البحث مشتق من قوائم `supportedActions/supportedTriggers` | سيصبح صحيحاً تلقائياً عندما تستبدل القوائم بمخرجات capability source الواحد. |
| Template filtering | **PARTIAL** | `RoutineTemplateCatalog` والقالب يمر عبر static `actionOptions` | لا يقيّم requirements للقالب قبل عرضه أو التطبيق. |
| Capability Center | **PARTIAL** | `CapabilityCenterScreen` موجود ويعرض ROM/SMS capabilities | snapshot ROM-centric؛ لا يستهلك `CapabilityDiagnostics` ولا يتحدث عند تغير Shizuku/permission. |
| Runtime updates | **UNSUPPORTED** | لا يوجد `StateFlow` أو callback coordinator للـregistry | UI لا يخفي/يعيد إظهار عناصر عند تغير backend state. |
| Workflow admission | **PARTIAL** | `CapabilityExecutionService` يمنع request mapped غير قابل للحل | automations القديمة لا تمر جميعها عبر requirement gate موحد قبل enable/run. |

## حقائق الأمان التي تقيد التنفيذ

`ShizukuCapabilityBackend` لا يعلن availability إلا عندما يعمل server، وتُمنح صلاحية Shizuku، ويكون UserService متصلاً، ويختار المستخدم Shizuku صراحةً في `ExecutionPolicy`. أما `RootCapabilityBackend` فلا يعلن إلا availability حية لـroot لعملية typed معروفة. لذلك لا يُستنتج من وجود تطبيق Shizuku أو binary root أن كل القدرة متاحة.

`CapabilityActionMapper` يتعمد ترك actions ذات semantics النظام أو Root أو Shizuku أو Accessibility أو command غير المقيدة خارج capability path؛ أي توسعة للواجهة يجب أن تكون قائمة requirements وصفية، ولا يجوز تحويل handlers legacy تلقائياً إلى privileged capabilities من دون implementation and verification حقيقيين.

## نقاط التوسعة الدنيا المقترحة

1. إنشاء `CapabilityRequirement` نقي في Domain يدعم `AllOf` و`AnyOf` و`Not` و`Capability`، ويعاد استخدامه من action/trigger/template/feature metadata.
2. إبقاء `CapabilityRegistry` و`CapabilityResolver` وحدهما؛ يضاف فوقهما snapshot service صغير cache-aware يستعلم descriptors بمنهج محدود ويرسل `StateFlow`.
3. تمثيل الحالة غير المتاحة بسبب Root/Shizuku/permission/Android/OEM كسبب typed من backend reports، لا كفحص UI مباشر.
4. استبدال `CompatibilityGate.supported*` بمخرج مشترك يجمع compatibility الحالية وcapability availability؛ لا تتغير `AutomationOptionCatalog` أو UX tiers.
5. تعميم `CapabilityCenterScreen` القائمة بدلاً من إنشاء صفحة إعدادات ثانية، مع عدم تقديم grant أو تنفيذ shell من الواجهة.
6. منع تفعيل أو تشغيل workflow يحتوي requirement غير محلول عبر validator/admission، مع إبقاء التعريف مرئياً في diagnostics فقط.

## ما لا يدخل هذه الدفعة

لا يضاف `REQUEST_INSTALL_PACKAGES` أو `MANAGE_EXTERNAL_STORAGE`. لا تُنشأ قناة ADB أو polling دائم أو foreground service دائم. لا تُعلن silent install أو Managed Google Play أو root filesystem أو Shizuku package manager كقدرات حتى توجد backend typed واختبارات تحقق حقيقية. لا تُزال automations القديمة أو تكسر؛ تُمنع من التفعيل/التشغيل عندما يثبت عدم توفر requirement.
