# NexaFlow v3.37.0 — تدقيق جاهزية محرك الأتمتة الإنتاجي

**تاريخ التدقيق:** 20 أغسطس 2026  
**المراجعة:** `b37c994` / `v3.37.0`  
**نطاق هذه المرحلة:** تدقيق معماري وتوثيق أدلة فقط؛ لا يعد هذا التقرير قبولاً على جهاز Android فعلياً.

> **القرار المعماري:** لا يجوز إنشاء Runtime أو Scheduler أو EventBus أو Queue أو مخزن حالة موازٍ. المسار الإنتاجي القائم هو `AutomationScheduler` → `AutomationAlarmReceiver` → `ExecutionEngine`، وتوجد مكونات أغنى لكن غير موصولة بهذا المسار (`AutomationWorkflowRunner` و`TaskManager` وDAG compiler). التوسعة الصحيحة هي ربط محدود ومدروس فوق هذه المكونات، لا إعادة تصميم التطبيق.

## منهج التصنيف

| التصنيف | المعنى في هذا التقرير |
|---|---|
| `REAL_DEVICE_VERIFIED` | تم إثباته على جهاز مادي؛ لا يوجد دليل قبول من هذا النوع في حالة المستودع الحالية. |
| `ANDROID_INTEGRATION_TESTED` | يغطيه اختبار Android/Robolectric أو مسار Android فعلي محدد. |
| `UNIT_TESTED_ONLY` | يغطيه اختبار وحدة أو اختبار JVM فقط. |
| `PARTIAL` | جزء من السلوك منفذ، لكن لا يغطي العقد المطلوب بالكامل أو لا يمر عبر Runtime الرئيسي. |
| `CONTRACT_ONLY` | نموذج/واجهة/مترجم موجود من دون ربط إنتاجي مثبت. |
| `UNSUPPORTED` | لا توجد آلية مثبتة في الشجرة الحالية. |

## خريطة التشغيل الفعلية

```text
Time trigger / Android event
  → AutomationScheduler (AlarmManager)
  → AutomationAlarmReceiver
  → ExecutionEngine
  → Constraint + maintenance-window gates
  → durable checkpoint / action registry
  → HistoryRepository + execution timeline
  → next alarm
```

يبدأ التطبيق المجدول والمراقبة والاسترداد في `NexaFlowApplication.onCreate`. الاسترداد الحالي يطالب بالـcheckpoints ويصنفها، ولا يعيد تشغيل Action تلقائياً. هذا اختيار سلامة صحيح للآثار الجانبية غير المعروفة، لكنه ليس استئناف Workflow كاملاً.

## المكونات القائمة وإعادة الاستخدام

| المكوّن | التنفيذ الحالي والدليل | قابل لإعادة الاستخدام | القيد أو الفجوة الفعلية |
|---|---|---:|---|
| الجدولة الزمنية | `AutomationScheduler` و`TimeTriggerCalculator` و`AutomationAlarmReceiver` | نعم | تدعم time triggers، لكنها لا تملك طابور priority دائم أو سياسة missed-workflow عامة. |
| التنفيذ الأساسي | `ExecutionEngine` مستخدم من Dashboard وDetails وAlarmReceiver | نعم | التنفيذ خطي بـ`mapIndexed`؛ لا ينفذ DAG أو branch/parallel من runtime الرئيسي. |
| DAG | `AutomationDagCompiler` + Kahn topological sort | نعم | compiler حقيقي ومختبر، لكن لا توجد استدعاءات إنتاجية له من `ExecutionEngine`. |
| Workflow interpreter | `WorkflowInterpreter` و`AutomationWorkflowRunner` | جزئياً | يدعم نماذج أغنى، لكنه مسار متوافق منفصل وليس مسار alarm/UI الأساسي. |
| Task priority/locks | `TaskManager` مع priority، retry، timeout، semaphore resources، cancellation | جزئياً | لا يوجد استعمال إنتاجي خارج الاختبارات؛ لا يجوز ربطه كطابور موازٍ بلا دمج صريح في `ExecutionEngine`. |
| checkpoints | `ActiveExecutionStore` + `DurableExecutionCheckpoint` | نعم | الحدود ثابتة: 128 checkpoint، والإقلاع يصنف الاسترداد ولا يستأنف Workflow تلقائياً. |
| idempotency للصيانة | `MaintenanceExecutionIdentity` + receipts في DataStore | نعم | يغطي occurrence للصيانة فقط؛ لا يوجد ledger موحد لكل عمليات package/file الحساسة. |
| recovery | `ExecutionRecoveryCoordinator` | نعم | يخرج `SAFE_RESUME_CANDIDATE` أو `VERIFY_OR_COMPENSATE_REQUIRED`، ولا ينفذ verifier/resumer. |
| المتغيرات | `RuntimeValue` و`VariableRepository` و`ScopedDataRuntime` | نعم | GLOBAL فقط durable؛ execution/workflow/node/action runtime-local، والـsecrets خارج GLOBAL محجوبة عمداً. |
| الشروط | `AutomationConstraintGate` و`ConstraintEvaluator` | نعم | AND ثابتة فقط؛ لا OR/NOT/nested expression DSL. |
| dry run | `WorkflowDryRunService` | نعم | validation + capability resolution فقط، لا محاكاة Actions أو trigger/context/recovery path. |
| history/health | Room history و`HealthRepository` و`AutomationHealthAnalyzer` | نعم | التقرير مشتق، ولا يوجد دليل UI صحي متكامل أو analytics dashboard كامل. |
| النسخ والاستعادة | `BackupManager` بصيغة v1 وpreflight واستيراد disabled-by-default | نعم | لا variables/settings/checksum/restore transaction شامل. |

## مخاطر لا يجوز تغطيتها بادعاء

> **نجاح البناء أو اختبارات الوحدة أو CI ليس قبول جهاز فعلي.** لا توجد في هذا المستودع نتيجة قبول موثقة لجهاز Stock أو Shizuku أو Root أو دورة reboot/Doze واقعية للإصدار v3.37.0. لذلك تبقى كل حالة `REAL_DEVICE_VERIFIED` غير مثبتة حتى تنفيذ هذا القبول وتسجيل نتائجه.

لا يحق لقالب التخزين ادعاء تنظيف تلقائي عام: Android لا يقدم API عامة لتفريغ cache أو حذف ملفات تطبيقات الغير للمستهلك. القالب الحالي يفتح الإعدادات الرسمية للمراجعة. وبالمثل، لا يحق للمسار Google Play ادعاء تحديث تطبيقات صامتة على هاتف شخصي.

## أقل خارطة توسع صحيحة

1. دمج preflight واحد في save/import/run: structural workflow validation + dependency graph validation + typed capability preview، من دون Scheduler جديد.
2. إدخال dependency analyzer تحذيري ودورات حقيقية فوق `AutomationDagCompiler` و`MaintenanceProfile`، قبل التفكير في branch/parallel.
3. ربط **محدود** لمفاهيم priority/resource admission القائمة بالـExecutionEngine، أو إبقاؤها غير معروضة حتى يصبح الربط production-safe؛ لا تستخدم TaskManager كـqueue موازٍ.
4. بناء recovery verifier/resumer لكل action آمن فقط بعد تعريف idempotency/verification/compensation، وعدم إعادة تشغيل `ACTION_STARTED` أو `ACTION_UNKNOWN` تلقائياً.
5. إضافة simulator يفسر trigger/context/constraints/actions على مستوى `would run`، فوق `WorkflowDryRunService` الحالي ومن دون dispatch حقيقي.
6. إكمال trace/health/analytics كـread-only projections من HistoryRepository وLogStore، من دون أرقام أداء تقديرية.
7. تنفيذ مصفوفة قبول Android على جهاز فعلي قبل اعتبار أي دعم root/Shizuku/OEM أو إعادة تشغيل أو Doze إنتاجياً.

| المجال | حالة التحقق | الدليل |
