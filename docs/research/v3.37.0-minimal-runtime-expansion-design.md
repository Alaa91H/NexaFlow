# NexaFlow v3.37.0 — تصميم التوسعة الدنيا لمحرك الأتمتة

**المدخلات:** تدقيق المستودع، عقود الصيانة الحالية، ووثائق Android الرسمية.  
**الحالة:** قرار تصميم قبل تعديل كود التشغيل.

> **مبدأ التنفيذ:** يبقى `AutomationScheduler` مجدول الوقت الوحيد، و`ExecutionEngine` مسار التنفيذ الإنتاجي الوحيد، و`ActiveExecutionStore` مصدر الاستمرارية الوحيد. لا يستعمل `TaskManager` كطابور Automation مستقل؛ بل لا يُربط إلا من خلال admission صغير ومدروس، أو يبقى مكوّناً داخلياً غير معروض حتى يثبت الربط.

## القرار المعماري

| القرار | المكوّن المعاد استخدامه | السبب | ما لا يُنشأ |
|---|---|---|---|
| قبول تشغيل موحد قبل actions | `ExecutionEngine` + `WorkflowValidator` + `MaintenanceReadinessEvaluator` | يمنع side effect قبل التحقق | Runtime جديد أو event bus جديد |
| تحليل اعتماديات عند الحفظ/الاستيراد | `MaintenanceProfile.dependencyAutomationIds` + `AutomationDagCompiler` | يرفض الدورات والتبعية الذاتية قبل التشغيل | dependency scheduler جديد |
| نتيجة تشغيل typed | `ExecutionRecord` + `ActionExecutionResult` + `HistoryRepository` | يمكن تفسير سبب المنع والتأجيل من التاريخ القائم | analytics database منفصلة |
| انتظار صيانة صادق | `MaintenanceReadiness` + alarm/monitor callbacks | حالة لا تعني failure ولا تعيد side effect | polling دائم أو foreground service دائم |
| استرداد آمن | `ActiveExecutionStore` + `ExecutionRecoveryCoordinator` | يمنع replay لآثار جانبية مجهولة | auto-replay عام |
| محاكاة قابلة للقراءة | `WorkflowDryRunService` + نفس validators/gates | read-only ولا تستدعي ActionHandler | sandbox code evaluator |

## دفعة التنفيذ الأولى: ما يجب تنفيذه الآن

تتكون الدفعة الأولى من **عقد اعتماديات قابل للتحقق، وpreflight موحد، وتقرير محاكاة واضح**. لا تضيف تفرعاً تنفيذياً أو parallel actions أو Queue. هذا يحقق تحسيناً إنتاجياً ملموساً مع أقل فرق معماري.

| النتيجة | التوسعة الدقيقة | نقطة الإدماج | القبول |
|---|---|---|---|
| dependency آمنة | Validator يستخرج dependency IDs من maintenanceProfile، ويرفض self-reference والمفقود والدورة | save/import/preflight؛ لا `ExecutionEngine` في البداية | tests: chain, missing, duplicate, self, cycle |
| تفسير executable | preflight يعيد workflow validity + dependency readiness + maintenance readiness + capability availability | `WorkflowDryRunService` موسع | tests: wouldRun/wouldWait/wouldReject |
| منع تشغيل dependency غير مكتملة | `ExecutionEngine` يتحقق من نجاح آخر occurrence/سجل dependency في النافذة قبل side effect | قبل checkpoint؛ بعد gates الحالية | test: no side effect when dependency is unavailable |
| سجل نتائج قابل للتفسير | typed outcome داخلي يحول إلى message localized في UI لاحقاً | History/ExecutionResultClassifier | test: reason code لا نص حر فقط |
| safety boundary | لا إعادة محاولة آلية لـACTION_STARTED/ACTION_UNKNOWN، ولا package install/cleanup جديد | `ExecutionRecoveryCoordinator` | test: recovery remains verify/manual |

## ما يؤجل عمداً

| المطلوب | سبب التأجيل |
|---|---|
| تفرع/parallel/loop في automation الرئيسي | توجد contracts في مسار بديل، لكن لا يوجد تشغيل production موحد أو policy للـcheckpoint/idempotency لكل branch. |
| ربط TaskManager مباشرة بكل Automation | سيصنع عملياً queue ثانية ويخاطر بسلوك متنافس مع AlarmManager/ExecutionEngine. |
| OR/NOT expression DSL | يحتاج grammar typed وmigration وUX وpreflight آمن؛ لا يدمج ضمن دفعة dependency دون تصميم مستقل. |
| resume تلقائي بعد process death | يحتاج verifier/compensator لكل Action؛ أي إعادة عامة الآن تخاطر بتكرار side effect. |
| locks durable وpriority multi-run | لا يكفي semaphore in-process؛ يلزم ownership/lease/recovery محدد قبل الادعاء بالدعم. |
| mode system وcapability center كامل | UI/domain واسع؛ لا يتطلبه تصحيح pipeline الأساسي. |
| تحديث Google Play أو تنظيف storage تلقائي عام | غير قابل للإثبات لتطبيق مستهلك؛ يبقى المسار الصادق المتدرج. |

## تسلسل التشغيل بعد الدفعة الأولى

```text
Trigger / Run now
  → structural validation
  → dependency validation and readiness
  → current constraint + maintenance readiness gates
  → checkpoint admission
  → sequential actions
  → history + typed outcome + occurrence receipt
```

الاعتماديات في هذه الدفعة **بوابة** لا مُجدول جديد: إذا لم تتحقق dependency، يسجل التشغيل حالة انتظار قابلة للتفسير ويُعاد تقييمه فقط عبر trigger/alarm/event القائم، لا عبر حلقة polling.

## شروط عدم التراجع

لا تُضاف إلى `AndroidManifest` صلاحيات `MANAGE_EXTERNAL_STORAGE` أو `REQUEST_INSTALL_PACKAGES`. لا تُستبدل alarms بـWorkManager للمهام ذات وقت المستخدم. لا تستخدم WorkManager لإدعاء exact time؛ فهو مناسب للصيانة المؤجلة والاحتفاظ فقط. لا تضع `dependency` أو `reason` كنص حر غير typed في database أو UI.

## مقياس نجاح الدفعة الأولى

تنجح الدفعة إذا تمكّن المستخدم أو الاستيراد من معرفة أن workflow غير صالح أو ينتظر dependency/نافذة/قدرة **قبل** side effect، مع سجل تاريخي صحيح واختبارات وحدة وتكامل للمسار. لا يُعلن دعم concurrency أو resumption أو automation graph كامل بهذه الدفعة.

## حد الاسترداد في هذه الدفعة

لا تضيف هذه الدفعة `resume` تلقائياً لـ`STARTED` أو`ACTION_COMPLETED`، ولا تعيد تشغيل `ACTION_STARTED` أو`ACTION_UNKNOWN`. السبب أن checkpoint القائم لا يحتفظ بحمولة Action غير قابلة للتغيير ولا بعقد verifier/compensator خاص بكل نوع Action. لذلك يبقى `ExecutionRecoveryCoordinator` مصنفاً للحالة، ويظل الانتقال من `SAFE_RESUME_CANDIDATE` إلى تنفيذ فعلي عملاً مستقبلياً مشروطاً بتحميل تعريف Automation نفسه والتحقق من نسخته وقدراته وidempotency قبل أي side effect.

هذا القيد لا يقلل من الاستمرارية الحالية: الـcheckpoint وoccurrence receipts ما زالا يمنعان التكرار الأعمى، والـhistory يسجل نتيجة التشغيل. لكنه يمنع الإعلان غير الصحيح عن "استئناف كامل بعد موت العملية" إلى أن يثبت ذلك باختبارات Android وجهاز فعلي.

## الأولوية والأقفال في الحالة الحالية

تم التحقق من أن `TaskManager` يملك priority queue وretry وtimeouts وresource semaphores، لكن لا توجد مراجع إنتاجية له من `ExecutionEngine` أو `AutomationAlarmReceiver`؛ ظهوره الحالي محصور في تعريفه واختبارات Android/JVM. لذلك لا يربط هذا الإصدار المكوّن بالـruntime ولا يعرض priority أو locks على أنها فعالة بين المهام المجدولة. أي دمج لاحق يجب أن يمر عبر نقطة admission واحدة قبل checkpoint، لا عبر queue ثانٍ إلى جانب `AutomationScheduler`.

## القوالب والإدارة

تمت مراجعة `RoutineTemplateCatalog`: القوالب الثلاثة للصيانة تنشئ مسودات `Automation` عادية مع `MaintenanceProfile` اختياري، وليست مسارات تنفيذ موازية. قالب التطبيقات يسجل عدم توفر Google Play بصيغة صادقة، وقالب التخزين يفتح صفحة المراجعة الرسمية، وقالب الأتمتة يرسل إشعاراً محلياً فقط. وبما أن `MaintenanceProfile` جزء من `Automation` المتسلسل، فإنه يعبر backup v1 مع بقاء الاستيراد معطلاً حتى مراجعة المستخدم؛ لا تحتاج هذه الدفعة إلى صيغة نسخ جديدة أو store خاص للقوالب.

## التفسير والصحة

`HealthRepository` الحالي واجهة read-only مشتقة من `HistoryRepository`، و`DashboardViewModel` يصنف النتائج الخاصة بتحديثات Google Play قبل عرضها. لذلك تتجنب هذه الدفعة أي رسالة "تم التشغيل" عندما تكون النتيجة `Skipped` أو عندما لا تتوفر واجهة Google Play رسمية. أما execution trace الدائم المفصل، analytics aggregate، وواجهة health dashboard المخصصة فما زالت عناصر لاحقة؛ لا تُنشأ لها قاعدة بيانات تحليلية أو أرقام تقديرية في هذه التغييرات.
